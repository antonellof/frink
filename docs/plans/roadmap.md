  - id: a0b-ideas-kept-from-the-deleted-policy
    content: "NOT A TASK YET, the ideas from `a0-dissolve-frink-edge`'s 8098 deleted lines that are worth NOT re-deriving. Each is good; each had an implementation that did not fit frink's shape, which is a different verdict from 'wrong'. (1) THE PREFIX-CACHE HANDOVER TRAP, and the one worth reading first. When a request offers a computed prefix to the radix tree, the span the tree ALREADY had is duplicates the request must free, and `InsertResult::cached_len` is deliberately documented as 'how much you must free' rather than 'how much I stored' -- read the other way it leaks a page per concurrent duplicate, forever, and the symptom is a pool that fills under load with nobody holding it. Freeing is ALSO not enough: the request is still READING those positions, so its page table must be REPOINTED at the tree's canonical pages first. CHECKED AGAINST THE LIVE PATH ON THIS BRANCH: `generate::publish_to_radix` has NEITHER defect, and avoids both structurally rather than by handling them -- pages are refcounted groups, the request keeps its own duplicates until its own `Drop`, and only `[cached_len, inserted_len)` gets the extra `retain_group`. Keep the rule written down anyway; the next implementation of this will not be refcounted by accident. (2) THE SWA TOMBSTONE RULE, which is a silent-corruption class and has no equivalent in frink today: a window request's out-of-window positions still hold FULL KV, so their pages publish normally, but their WINDOW slots are gone -- the tree must TOMBSTONE below that frontier rather than adopt them as window-live, or a later request matches the node and gathers through a mapping that reads the reserved sentinel. Slot 0's bytes in every window head, on a path that never errors. This matters the moment frink gives sliding-window models a shared prefix cache. (3) THE FOUR SUPERVISOR RULES, if frink ever grows a daemon that spawns an engine: a retried start must not become a second engine (two on one GPU is OOM at best, two serving different weights on one port at worst); ONE party reaps and everyone else waits on what it publishes, because a poll TRANSIENTLY LIES while the monitor holds the lock; the stop-requested latch is set when the stop is REQUESTED, not when it completes, or a crash mid-stop reads as an unplanned death and the supervisor restarts what you were stopping; and re-adoption keys on `(pid, start_time, argv, port)` because PIDs recycle and `start_time` is the only part a recycled PID cannot reproduce. (4) DEFERRED FREES ACROSS A BATCH: within one batch several requests commit, and a page freed by the first must not reach the third while the second is still reading it. (5) An exact-TOKEN-length prompt for a serving benchmark needs a FIXED-POINT loop, because decode-then-encode is not the identity -- the tokenizer merges adjacent pieces, so a prompt built from N ids re-encodes SHORTER and a run labelled '512-token prompts' quietly benchmarks something else. Frink's own `bench -p 512` is unaffected (it tokenizes in-process); this bites any HTTP-side serving benchmark."

# The roadmap

Every open item, merged by what the work is rather than by which
document raised it. The goal is in [`north-star.md`](north-star.md).

**The rule that overrides the order: shipped and working beats big and
undone.** An item that cannot be cut into steps which each land, and
each leave the engine better, is filed wrong. Before starting anything,
name what a user can do after step one that they could not do before.
If the answer is "nothing yet, but later", cut it smaller.

**What `status` means here.** `pending` is open work. `done` is landed
AND verified against the code, never against this file's own claim: a
merged PR once marked `paged-decode-path` complete while it returned
wrong tokens on Metal. `note` is a rule or a finding that is worth not
re-deriving and is not a task. An item can be `pending` with most of its
content closed, and when it is, the content says which parts.

Two items are big enough to have their own design document:

- [`model-layer-reorg.md`](model-layer-reorg.md), splitting the
  decoder so architectures scale. It was 6438 lines when that document
  was written and is 6702 today, the first time it has shrunk.
- [`out-of-core-moe.md`](out-of-core-moe.md), running a 155 GB model on
  a 32 GB machine.

## Order, and what each step ships

| # | Theme | Ships what |
|---|---|---|
| **1** | Fix what is wrong, and close the oracle's hole | Correct output on models that run today. Small, immediate |
| **2** | Model layer: audit, vocabulary, then split | A correctness fix per audit finding, then one architecture at a time |
| **3** | Close the 41: **inversion done, triage done**, five closed, now audit outward | Honest refusals instead of silent wrong answers, each naming what is missing |
| **4** | Out-of-core MoE, and one large real checkpoint | A model that did not fit, running. First milestone is "does it load" |
| **5** | CPU decode scaling | One item carrying most of the remaining CPU gap |
| **6** | Hardware reach: backend seam, then Vulkan | Every AMD and Intel GPU, currently none |
| **7** | The rest: embeddings, quants, serving, measurement | Breadth, once the above hold |

## The rules that keep being re-learned

**A plan's own status field is a claim, not evidence.** A merged PR once
marked `paged-decode-path` complete while it returned wrong tokens on
Metal.

**One agent owns a file.** Two branches editing one file produce a merge
nobody can review, and this project has had a branch silently revert
three others.

**No agent runs benchmarks.** A loaded host reads 25-45% low.

**Refusing is not a defect.** llama.cpp will often run something
approximately; this project stops and names what is missing.
